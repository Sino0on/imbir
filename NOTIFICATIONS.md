# Уведомления — как работают и что приходит

## Как это работает в целом

1. Бэкенд сам создаёт уведомление, когда происходит одно из перечисленных ниже событий (запись создана/подтверждена/отменена/завершена, новый отзыв). Фронту ничего создавать не нужно.
2. Уведомление привязано к конкретному пользователю (`user`) — врачу, клинике или пациенту, в зависимости от события.
3. Счётчики (шапка сайта, пункты меню кабинета) берутся из отдельной лёгкой ручки `unread-count`, а НЕ считаются на клиенте по списку — список постраничный, полной картины на фронте нет.
4. Клик по уведомлению — по `type` + `payload` можно построить прямую ссылку на нужный объект (запись/отзыв), не открывая общий список.

## Эндпоинты

Базовый префикс: `/api/notifications/`

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/api/notifications/` | Список уведомлений, с пагинацией |
| `GET` | `/api/notifications/unread-count/` | Счётчик непрочитанных — общий и по типам |
| `PATCH` | `/api/notifications/{id}/read/` | Отметить одно прочитанным |
| `PATCH` | `/api/notifications/read-all/` | Отметить все прочитанными |

Все требуют авторизации (`Authorization: Bearer <token>`).

### `GET /api/notifications/`

Query-параметры:
- `page`, `page_size` — как везде в API (стандартная пагинация).
- `is_read` — `true` / `false`, необязательный. Без параметра — все уведомления.

```
GET /api/notifications/?page=1&page_size=20&is_read=false
```

Ответ:
```json
{
  "data": [
    {
      "id": 1042,
      "type": "appointment_confirmed",
      "title": "Запись подтверждена",
      "body": "Ваша запись на 05.09.2026 в 11:00 подтверждена.",
      "is_read": false,
      "payload": { "appointment_id": 100007, "doctor_id": 77, "clinic_id": null, "date": "2026-09-05", "time": "11:00" },
      "created_at": "2026-08-29T09:12:03Z"
    }
  ],
  "pagination": { "page": 1, "page_size": 20, "total": 37, "total_pages": 2 }
}
```

> **Важно:** раньше эта ручка отдавала `{"data": [...], "unread_count": N}`. Поле `unread_count` отсюда убрано — теперь оно только в `unread-count/` (см. ниже). Если где-то на фронте читали `unread_count` именно из списка — нужно перевести на новую ручку.

### `GET /api/notifications/unread-count/`

```json
{
  "total": 5,
  "by_type": { "appointment_confirmed": 2, "new_review": 1, "appointment_cancelled": 2 }
}
```
- `total` — сумма всех непрочитанных, для бейджа в шапке.
- `by_type` — сколько непрочитанных каждого типа. Ключей в `by_type` столько, сколько реально есть непрочитанных типов — если по какому-то типу 0, его в объекте не будет (не нужно ожидать все 7 ключей всегда).

Для пунктов меню кабинета (например «Записи» отдельно от «Отзывы») суммируйте нужные типы из `by_type` на своей стороне — например бейдж на разделе записей = `appointment_created + appointment_confirmed + appointment_cancelled + appointment_completed + appointment_reminder`.

### `PATCH /api/notifications/{id}/read/`

Без тела запроса. Ответ — сам обновлённый объект уведомления (см. форму выше).

### `PATCH /api/notifications/read-all/`

Без тела запроса.
```json
{ "marked_read": 12 }
```

## Типы уведомлений и что лежит в `payload`

`payload` — фиксированный набор полей на каждый `type`, чтобы можно было построить ссылку без похода в общий список.

| `type` | Когда создаётся | Кому | `payload` |
|---|---|---|---|
| `appointment_created` | Пациент создал новую запись | врачу **и** клинике (если оба есть) | `{"appointment_id": 100007, "doctor_id": 77, "clinic_id": null, "date": "2026-09-05", "time": "11:00"}` |
| `appointment_confirmed` | Запись переведена в статус «подтверждена» | пациенту | то же самое, `doctor_id`/`clinic_id` — участники записи |
| `appointment_cancelled` | Запись отменена | если отменил пациент — врачу и клинике; если отменил врач/клиника — пациенту | то же самое |
| `appointment_completed` | Запись переведена в «завершена» | пациенту | то же самое |
| `new_review` | Оставлен новый отзыв | тому, о ком отзыв (врачу или клинике) | `{"review_id": 9, "target_type": "doctor", "target_id": 77}` |
| `appointment_reminder` | **Ещё не реализовано** — нужен планировщик (напоминание за сутки до приёма) | пациенту | тот же формат, что у `appointment_confirmed` |
| `new_message` | **Ещё не подключено** — у чата свой канал доставки, дублировать в уведомления пока не стали | — | `{"room_id": 7}` (формат готов, но событие никогда не создаётся) |
| `system` | Служебное, вручную/на будущее | любой | произвольный, не гарантирован |

### Как строить ссылку по `type`

```
appointment_created / confirmed / cancelled / completed / reminder
  → ссылка на карточку записи, id = payload.appointment_id

new_review
  → ссылка на профиль врача или клиники (смотря по payload.target_type),
    id = payload.target_id; сам отзыв — payload.review_id, если нужен якорь

new_message
  → пока не создаётся, ссылку строить не на что
```

`doctor_id`/`clinic_id` в appointment-уведомлениях — это публичные id (`user_id`), как везде в API (`/api/doctors/{id}/`, `/api/clinics/{id}/`), а не внутренние идентификаторы.

## Известные ограничения

- **Напоминания за сутки не приходят** — это отдельная задача на периодическую фоновую джобу, ещё не сделана. Пока `appointment_reminder` просто никогда не создаётся.
- **Новые сообщения в чате не дублируются сюда** — если понадобится единый бейдж «уведомления» вместе с непрочитанными чатами, скажите, подключим `new_message`.
